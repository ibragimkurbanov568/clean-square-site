# Аудит безопасности и производительности: CleanLink

Источники: `docs/01-spec.md` (роли, правила доступа, требования безопасности), `docs/04-architecture.md`
(контракт API, схема данных), `docs/07-integration.md` и `docs/08-qa.md` (что уже проверено и
починено — этот отчёт не дублирует прошлые находки, только то, что осталось).

Метод: построчное чтение всех приватных маршрутов (`backend/src/routes/*.ts`), всей
криптографии/сессий (`backend/src/lib/crypto.ts`, `jwt.ts`, `session.ts`, `totp.ts`), всех
Zod-схем, миграций (`migrations/*.sql`) и фронтенда (поиск `dangerouslySetInnerHTML`, редиректов,
загрузок). Каждая находка ниже подтверждена чтением конкретного кода (путь:строка) — ничего не
выдаётся за проблему без указания, где именно она в коде.

`npm test`, `npm run typecheck`, `npm run lint`, `npm run build` — зелёные в обоих workspace
после всех правок этой сессии (см. §4).

### Что проверено и подтверждено рабочим (без находок)

Ниже — контрольный список из задания, пройденный по каждому пункту с указанием, где именно
проверено, чтобы не выдавать непроверенное за проверенное:

- **JWT access+refresh в HttpOnly cookies** (`backend/src/lib/session.ts`, `jwt.ts`):
  `httpOnly: true` всегда, `secure: env.ENVIRONMENT === 'production'` (корректно: `false` в dev
  по HTTP, `true` в проде по HTTPS — иначе cookie не долетит по HTTP dev-серверу), `sameSite:
  'Lax'`. TTL: access 15 мин, refresh 30 дней (`rememberMe`) / 1 день (сессия). Refresh-сессия
  (`sid`) — отдельная запись в KV `SESSIONS`, логаут (`revokeCurrentSession`) удаляет её из KV —
  подтверждено рабочим тестом `backend/tests/integration/auth.test.ts` («logout отзывает сессию:
  refresh после logout → 401»). Просроченный/подделанный access-токен: `verifyAccessToken`
  бросает исключение при неверной подписи/`exp` — `requireAuth` ловит и возвращает 401
  (`backend/src/middleware/auth.ts:29-34`) — подтверждено `auth.test.ts`.
- **Разделение ролей client/company и владение ресурсом на каждом приватном эндпоинте.**
  Построчно пройдены все файлы `backend/src/routes/*.ts` (`orders.ts`, `chats.ts`, `reviews.ts`,
  `services.ts`, `promotions.ts`, `companies.ts`, `favorites.ts`, `stats.ts`, `uploads.ts`,
  `admin.ts`): каждый эндпоинт, меняющий или читающий приватные данные, сверяет владельца через
  `company.user_id === c.get('userId')` / `order.client_id === c.get('userId')` /
  `loadChatParticipant()` — **сверка всегда идёт с ID из подписанного JWT (`c.get('userId')`),
  никогда с параметром запроса напрямую** (классический IDOR-паттерн «доверяем `req.body.userId`»
  нигде не встречен). Неверифицированная компания: `services`/`promotions` возвращают `{items:
  []}` на бэкенде до всякого рендера фронтенда (`services.ts:26-28`, `promotions.ts:41-43`),
  `POST` создания услуг/акций/приёма заказов явно проверяет `is_verified` и отдаёт 403/400
  (`services.ts:48-50`, `promotions.ts:73-75`, `orders.ts:54-56`) — подтверждено существующими
  `backend/tests/integration/{orders,services,promotions,companies}.test.ts` (написаны на шаге
  QA, не менялись в этом аудите, перечитаны как часть проверки).
- **Валидация всех входных данных через Zod.** `grep` по всем route-файлам подтвердил: каждое
  тело запроса (`c.req.json()`) и каждый query/param (`c.req.query()`/`c.req.param()`) проходит
  через `.parse()` соответствующей Zod-схемы без исключений — необработанного «сырого» доступа к
  входным данным не найдено.
- **SQL: нет конкатенации в запросы к D1.** Все `queryOne`/`queryAll`/`execute`
  (`backend/src/db/client.ts`) используют `.bind(...params)`; единственные места, где в шаблонной
  строке SQL встречается `${...}` — это (а) статические фрагменты запроса, вынесенные в константы
  (`COMPANY_SELECT`, `ORDER_SELECT`, `CHAT_LIST_SELECT` и т.д.), (б) whitelisted-маппинг «ключ
  Zod-схемы → имя SQL-колонки» на статических объектах (`UPDATE_COLUMN_MAP` в `companies.ts`,
  `services.ts`, `promotions.ts` — ключи фиксированы кодом, не приходят от пользователя), (в)
  значение из `Zod`-`enum()` (`SORT_SQL[query.sort]`, `ORDER_BY[input.sort]` — сам `sort` уже
  ограничен перечислением на этапе валидации). Ни одно пользовательское строковое значение не
  попадает в SQL иначе чем через `?`/`.bind()`.
- **XSS на фронтенде.** `grep -r dangerouslySetInnerHTML|innerHTML frontend/src` — ноль
  совпадений. Пользовательский текст (названия компаний, тексты отзывов/сообщений, ответы
  компании) везде рендерится через обычный JSX `{text}` — React экранирует по умолчанию, как и
  зафиксировано в `docs/01-spec.md` («дополнительная санитизация HTML не требуется, т.к. rich-text
  ввод не поддерживается»). Единственный найденный XSS-вектор — не в рендере текста, а в загрузке
  файлов (см. находку №1 выше, уже починена).
- **CSRF.** Cookie-аутентификация защищена комбинацией `SameSite=Lax` (браузер не приложит cookie
  к кросс-сайтовому `fetch`/`XHR` ни при каком методе, и не приложит к кросс-сайтовому `POST`-
  сабмиту формы — только к top-level GET-навигации) + `HttpOnly` (JS с чужого origin не может
  прочитать/подставить токен вручную) + строгий CORS (`hono/cors`, `origin: (_, c) =>
  c.env.CORS_ORIGIN`, конкретное значение, не wildcard, `credentials: true` — `backend/src/index.
  ts:28-35`) — кросс-origin `fetch(..., {credentials:'include'})` с чужого домена получит отказ
  браузера ещё до отправки тела запроса (preflight не пройдёт для non-simple методов
  PATCH/DELETE, а для простых — ответ не будет читаемым и cookie всё равно не будет отправлен
  из-за `SameSite=Lax`). Отдельный CSRF-токен избыточен при этой комбинации — находки нет.
- **Rate limiting.** Точечно подключён (не глобально) к каждому чувствительному эндпоинту:
  `register` (оба), `login`, `login/2fa`, `forgot-password`, `reset-password`, `order-create`,
  `review-create`, `chat-message` (`grep -rn "rateLimit(" backend/src/routes` подтверждает все 8
  точек подключения). Идентичность — `userId` для авторизованных маршрутов, иначе
  `cf-connecting-ip` (`backend/src/middleware/rateLimit.ts:21-22`). **Обход сменой заголовка:**
  `CF-Connecting-IP` — заголовок, который **сам Cloudflare** устанавливает на границе сети и
  замещает любое клиентское значение с тем же именем при реальном деплое на Workers (недокументно
  не подделываемый клиентом факт инфраструктуры CF, не особенность этого кода) — так что в
  продакшене смена заголовка не даёт обхода. Ограничение отмечаю честно: при локальном
  `wrangler dev`/тестах без реального прохождения через Cloudflare-границу этот заголовок
  действительно приходит от клиента как есть — это ограничение локальной среды разработки, а не
  уязвимость продакшен-деплоя, поэтому не выношу в починку.
- **AES-256-GCM.** IV — `crypto.getRandomValues(new Uint8Array(12))` **заново на каждый вызов**
  `encryptField()` (`backend/src/lib/crypto.ts:95`), не переиспользуется и не выводится
  детерминированно — подтверждено также интеграционным тестом `chats.test.ts` (QA-отчёт,
  §0): два одинаковых по тексту сообщения дают разный шифротекст. Ключ — `env.ENCRYPTION_KEY`,
  небезопасного дефолта в коде нет (`importAesKey` бросает исключение, если ключ не декодируется
  ровно в 32 байта — небезопасный «пустой ключ по умолчанию» невозможен структурно). Секреты
  нигде не хардкожены в исходниках — см. следующий пункт.
- **Секреты в репозитории.** `git ls-files | grep -iE '\.env$|\.dev\.vars$|secret|\.pem$|\.key$'`
  — пусто. `.gitignore` (корень) явно исключает `.env`, `.env.local`, `.dev.vars`,
  `.wrangler/`. `.env.example`/`backend/.dev.vars.example`/`frontend/.env.example` содержат
  только явно подписанные плейсхолдеры (`change-me-...`, `dev-access-secret-change-me...`) —
  ни одного похожего на настоящий продовый секрет значения. `migrations/0003_seed_demo_data.sql`
  прямым текстом комментирует: «Пароль у всех демо-пользователей ниже: password123» — демо-статус
  не скрыт. `wrangler.toml` — `database_id`/KV `id` — буквально нули-плейсхолдеры с инструкцией
  в комментарии, как получить настоящие. Находок нет.
- **Утечки в ответах API.** `mapCurrentUser()` (`backend/src/lib/mappers.ts`) явно перечисляет
  поля белым списком (`id, email, role, username, city, avatarUrl, totpEnabled, company?`) —
  `password_hash`/`totp_secret`/`password_reset_token` физически не могут просочиться, т.к. не
  входят в маппер, а `grep` по всем роутам (`c.json(user`, `...user`, `c.json(row`) не нашёл ни
  одного места, где строка БД целиком отдаётся в ответ напрямую. Чужие email/телефоны: список
  заказов/отзывов/чатов всегда выбирается через `WHERE client_id = ?`/`company_id = ?` с текущим
  `userId`, отдельного «показать все контакты» эндпоинта нет. Находок нет.
- **Логирование в R2.** `logAuditEvent()` (`backend/src/lib/queue.ts:88-99`) пишет только
  структурные метаданные события (`orderId`, `companyId`, `clientId`, `serviceId`, `userId`,
  `resetUrl` — только в demo-режиме без `RESEND_API_KEY`, см. находку №5 выше про сам токен) —
  **пароли и тексты сообщений чата в аудит-лог не попадают ни в каком вызове** (`grep -rn
  "logAuditEvent(" backend/src` — все 3 точки вызова перечислены и проверены построчно: логин/
  восстановление пароля не логируют пароль, `order.created.notification` не логирует текст
  сообщений). Доступ к самому аудит-логу дополнительно ограничен находкой №2 (починено).

## 5. Итог для оркестратора

- **Критичных находок: 1** (stored XSS через загрузку SVG-аватара/обложки/обоев с последующим
  выполнением скрипта на origin API и захватом cookie-сессии жертвы, открывшей ссылку на
  загруженный файл) — **починено** (белый список конкретных растровых MIME-типов вместо префикса
  `image/*`, `X-Content-Type-Options: nosniff`, регрессионный тест).
- **Важных находок: 2** — обе **починены**: (а) публичная отдача R2-объектов по ключу без
  белого списка префиксов (потенциальный путь к аудит-логу, где в demo-режиме без
  `RESEND_API_KEY` лежит ссылка восстановления пароля — практически неэксплуатируемо без знания
  случайного UUID-ключа, но исправлено как defense-in-depth); (б) конкретная точка использования
  известной умеренной уязвимости `react-router-dom` (`returnTo` в `/login`) закрыта валидацией
  на уровне приложения.
- **Незначительных находок: 2** — обе с точечным исправлением: timing-safe сравнение
  `ADMIN_SECRET`; наблюдение про `password_reset_token` в открытом виде (не эксплуатируемо без
  уже имеющегося доступа к БД) зафиксировано как **осознанно принятый риск**, не чинилось —
  решение о хэшировании токенов восстановления пароля оставлено владельцу проекта при переходе к
  проду.
- **Что осталось и требует решения владельца проекта:** обновление `react-router-dom` с 6.x до
  7.x, чтобы закрыть саму уязвимую зависимость (а не только конкретный вектор в этом приложении)
  — мажорное ломающее обновление роутинга всех 24 маршрутов, осознанно вне рамок минимального
  точечного аудита; решение, что делать с `password_reset_token` (хэшировать перед сохранением)
  при переходе к продакшен-деплою.
- **Производительность:** главный JS-бандл фронтенда уменьшен с 735.66 KB до 326.48 KB (−56%
  сырого размера, −55% gzip) добавлением маршрутного code splitting; N+1-запросов к D1 в
  списковых эндпоинтах не найдено (все уже используют один SQL-запрос с `JOIN`/подзапросами +
  `LIMIT/OFFSET` на уровне SQL); индексы на всех фильтруемых/сортируемых колонках подтверждены
  соответствующими текущим `WHERE`/`ORDER BY`.
