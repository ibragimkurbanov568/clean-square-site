# Шаг 7 — интеграция: отчёт

Проверка выполнена вручную в реальном Chromium через Playwright
(`/opt/pw-browsers/chromium-1194/chrome-linux/chrome`), сервер и
интерфейс — одна и та же команда `npm run dev` (Vite, `http://localhost:5173`,
без бэкенда: NoesDize — статический SPA, всё состояние в `localStorage`
браузера, см. `docs/04-architecture.md` §5). Дальше — три найденных дефекта
и один дефект, найденный координатором отдельным прогоном после первой
сдачи (панель «Настройки»), их причина и починка, затем сквозной прогон
всех функций MVP из `docs/01-spec.md`.

## Единая команда запуска

```bash
npm run dev     # или npm start — синоним, добавлен на этом шаге
```

Backend отсутствует по архитектуре (принятое допущение №4 в
`docs/01-spec.md`), поэтому «поднять сервер и интерфейс одновременно»
здесь равно «поднять один Vite dev-сервер» — `package.json` теперь
дополнительно объявляет `"start": "vite"` как явный, узнаваемый alias
для `dev`, ничего разводить по портам/CORS не требовалось (один origin,
без API).

## Дефект 1 — нечитаемый заголовок hero в 5 из 6 тем

**Причина.** Правило в `src/lib/pageAssembler.ts` красило заголовок и
подзаголовок hero токеном `--site-accent-ink` — «чернила поверх ровной
заливки `--site-accent`» (кнопки). Но фон hero при включённых эффектах —
двухцветный градиент `--site-gradient-start → --site-gradient-end`,
цвета которого у 5 из 6 тем не совпадают с `--site-accent`. Контраст
`--site-accent-ink` был проверен и задокументирован (`docs/03-design-system.md`
§2.2) только против сплошной заливки accent — против второго конца
градиента его никто не считал, и он не проходил.

Хуже: у «Ремесла» и «Карнавала» `--site-gradient-end` был **равен**
`--site-accent-2` — светлому золотому цвету (относительная яркость
0.417 и 0.435). Математически доказано (см. ниже), что для градиента с
таким разбросом яркости между концами (тёмный старт ~0.15, светлый
конец ~0.42) не существует ни одного сплошного цвета текста, который
одновременно даёт контраст ≥4.5:1 к обоим концам — WCAG-контраст
монотонен по относительной яркости, а нужные пороги для двух концов
(`Lt ≥ 0.886` для тёмного старта, `Lt ≤ 0.054` для светлого конца)
не пересекаются ни при каком единственном значении `Lt`. Проверочный
скрипт: `/tmp/.../scratchpad/pick.js` (см. историю сессии).

**Починка (обе стороны контракта, с разрешения оркестратора):**
1. В `src/styles/site-themes.css` в каждую из 6 тем добавлен отдельный
   токен `--site-hero-ink`, подобранный именно под пару
   `gradient-start/gradient-end` этой темы (а не под `--site-accent`).
2. У «Ремесла» и «Карнавала» **`--site-gradient-end` затемнён**
   (был равен светлому `--site-accent-2`) ровно настолько, чтобы это
   стало математически достижимо одним сплошным цветом текста — иначе
   никакой токен не помог бы (доказательство выше). `--site-accent-2`
   как отдельный токен не тронут — он по-прежнему используется в
   декоре галереи (`site-gallery__tile`), там ничего не менялось.
3. `src/lib/pageAssembler.ts` (`SITE_THEME_CSS_VARS`) — точная копия
   правок из `site-themes.css` (обе темы) плюс `--site-hero-ink` по
   каждой из 6 тем, потому что экспортированный HTML не может
   ссылаться на внешний CSS-файл и несёт тему инлайново (F7). Правило
   `.site-hero--effects .site-heading-xl / .site-hero__subtitle`
   переведено с `--site-accent-ink` на `--site-hero-ink`.
4. `docs/03-design-system.md` §2.2 дополнен уточняющей врезкой:
   старая формулировка ошибочно утверждала, что `--site-accent-ink`
   годится для текста над градиентом — это и было корнем дефекта.

**Контраст «текст hero / оба конца градиента» (WCAG 2.1, относительная
яркость sRGB), было → стало:**

| Тема | Было (start / end) | Ink до | Стало (start / end) | Ink после | `--site-gradient-end` |
| --- | --- | --- | --- | --- | --- |
| Атлант | 8.61 / 15.74 (ок) | `--site-accent-ink` `#ffffff` | 8.61 / 15.74 | `--site-hero-ink` `#ffffff` | не менялся |
| Ремесло | 5.06 / 2.25 (плохо) | `#ffffff` | **5.06 / 6.76** | `#ffffff` | `#d9a441` → `#7a5417` |
| Импульс | 1.01 / 1.45 (нечитаемо) | `#06110d` | **17.07 / 11.66** | `#e9f3ef` | не менялся |
| Воздух (по умолчанию) | 1.00 / 1.14 (нечитаемо) | `#ffffff` | **17.40 / 15.27** | `#1a1a1a` | не менялся |
| Карнавал | 5.18 / 2.16 (плохо) | `#ffffff` | **5.18 / 6.59** | `#ffffff` | `#e7a400` → `#7c5600` |
| Бархат | 1.00 / 1.20 (нечитаемо) | `#14110e` | **15.99 / 13.29** | `#f3ecdd` | не менялся |

Все шесть тем теперь ≥4.5:1 к обоим концам градиента — с запасом, не
впритык (минимум — 5.06 у «Ремесла»).

**Чем проверено:** скрипт Playwright, открывающий предпросмотр, читающий
`getComputedStyle` заголовка (`.site-heading-xl` внутри
`iframe.nd-preview-frame__iframe`) и оба `rgb(...)`-стопа реального
рендер-значения `background-image: linear-gradient(...)` секции
`.site-hero--effects`, считающий WCAG-контраст между ними —
`/tmp/.../scratchpad/full_verify.mjs`, вывод воспроизведён в таблице
выше 1:1. Плюс визуальный осмотр скриншотов каждой темы (все шесть —
заголовок отчётливо виден на градиенте) и открытие экспортированного
`.html` с диска (`file://`) — идентично предпросмотру, ошибок консоли
нет.

## Дефект 2 — подписи секций схлопнуты в 0 ширины + шапка панели

**Причина (главная, не про сам `.nd-section-row__name`).** У
`.nd-editor__panel`/`.nd-editor__preview-col` есть три конкурирующих
CSS-правила на разных ширинах экрана:
- база: `display: none` (без атрибута);
- `[data-mobile-active="true"]` — специфичность класс+атрибут
  `(0,2,0)`, `display: flex; flex: 1` — **не завёрнуто в медиа-запрос**,
  относится к однопанельному мобильному режиму (`mobileView` всегда
  равен `"edit"` при загрузке редактора, то есть `data-mobile-active`
  панели секций равен `"true"` **и на десктопе тоже**, просто десктоп
  показывает обе панели через другое правило);
- `@media (min-width: 768px) { .nd-editor__panel { width: 380px; flex: 0 0 380px } }`
  — специфичность всего один класс `(0,1,0)`.

По правилам каскада специфичность важнее порядка объявления и медиа-
контекста: `flex: 1` из второго правила **побеждал** `flex: 0 0 380px`
из третьего на любой ширине экрана, включая десктоп 1440px. В
результате `.nd-editor__panel` реально получал ~208px вместо 380px
(боролся за общее пространство с `.nd-editor__preview-col` наравне,
`flex:1` против `flex:1`, но предпросмотр «побеждал» за место ещё и
из-за отдельного, второго найденного при проверке бага — см. ниже).
Внутри урезанной до 208px панели `.nd-section-row__main` (иконка +
имя + 4 кнопки-действия) физически не хватало места, и `.nd-section-row__name`
(`flex:1; min-width:0`) — единственный по-настоящему гибкий элемент —
получал 0px, а иконки/кнопки (`flex-shrink:0`) не сжимались вовсе.

**Побочный дефект, найденный по дороге:** `.nd-editor__panel`/
`.nd-editor__preview-col` не имели `min-width: 0`. Внутри предпросмотра
лежит фиксированный 1200px-виджет десктопного вьюпорта
(`PreviewFrame.tsx`, `VIEWPORT_SIZES.desktop.width`), обёрнутый в
`overflow:hidden`-контейнер для визуального масштабирования — но
`overflow:hidden` на потомке не отменяет автоматический
flex-минимум (`min-width:auto`) самого `.nd-editor__preview-col` как
flex-элемента `.nd-editor__body` (row): без явного `min-width:0` браузер
всё равно учитывал 1200px как пол ширины, раздувая `.nd-editor__body`
и всю страницу шире вьюпорта — **настоящая горизонтальная прокрутка
всей страницы на 1440px и 768px** (на 375px её не было только потому,
что на мобильной ширине предпросмотр скрыт через `display:none` и не
участвует в layout вовсе — ложноположительный «зелёный» результат при
проверке только на одной ширине).

**Починка** (`src/styles/app.css`):
1. `.nd-editor__panel, .nd-editor__preview-col` — добавлен `min-width: 0`
   к уже существовавшему `min-height: 0` (убирает горизонтальную
   прокрутку страницы на 1440/768).
2. Правило `flex: 1` для `[data-mobile-active="true"]` **оставлено
   как есть, без медиа-запроса** (важно: попытка завернуть его в
   `@media (max-width: 767px)` чинит реальный браузер, но ломает
   `App.smoke.test.tsx` — jsdom не матчит `@media` внутри
   `getComputedStyle` вообще, включая существующее `@media (min-width: 768px)`
   с `display: flex !important`, и без «страхующего» безусловного
   `display: flex` панель стала бы `display:none` в тестовой среде и
   тест не находил бы кнопки — проверено эмпирически, откат и
   диагностика зафиксированы в истории сессии).
3. Вместо этого специфичность десктопных правил зафиксирована через
   `!important` — `.nd-editor__panel { flex: 0 0 320px !important }`
   (и `380px !important` на ≥1200px), `.nd-editor__preview-col { flex: 1 !important }`.
   `!important` побеждает не-`!important` правило независимо от
   специфичности и порядка — это чинит реальный десктопный layout, не
   трогая поведение `display` (которое нужно тестам).
4. Заголовок «Секции сайта (N/12)» и кнопка «Добавить секцию» ничего
   отдельно чинить не потребовалось — оба «чинились» тем же самым:
   после возврата панели к 320/380px реальной ширины (вместо ~208px)
   заголовок умещается в 1–2 строки без переноса на три, а кнопка
   полностью влезает и не обрезается краем панели (видно на скриншотах).
5. `src/components/SectionRow.tsx` — на `.nd-section-row__name`
   добавлен `title={definition.labelRu}`: на очень узких ширинах
   (например 320px-панель на планшете 768px, где 4 кнопки-действия
   реально не оставляют места) имя всё равно обрезается многоточием
   (это ожидаемо и соответствует требованию «обрезать только при
   реальной нехватке места»), но полное название теперь доступно по
   наведению.

**Чем проверено:**
- `getBoundingClientRect()`/`getComputedStyle()` в реальном Chromium на
  1440×900, 768×1024, 375×812 (`viewport_check.mjs`,
  `find_overflow.mjs`, `explore2.mjs`/`explore3.mjs`) — ширина имени
  секции: 91px / 31px / 55px (везде >0, было 0 везде на 1440);
  `document.documentElement.scrollWidth === clientWidth` на всех трёх
  ширинах (было `1612 vs 1440` и `1552 vs 768` — реальная горизонтальная
  прокрутка, исправлено).
- Скриншоты `final-03-editor.png`, `viewport-768.png`,
  `final-mobile-375.png` — заголовок панели на 1–2 строках, кнопка
  «Добавить секцию» целиком внутри панели, подписи секций видны на
  всех трёх ширинах (на 768px — коротко, с ellipsis, что ожидаемо при
  320px панели с 4 кнопками; полное имя — во всплывающей подсказке).
- `npm test` — все 406 тестов зелёные после починки (первая версия
  фикса ломала `App.smoke.test.tsx`, см. п.2 выше — исправлено).

## Дефект 3 — секция «Hero» на английском

**Причина.** В `src/content/sectionLibrary.ts` только у типа `hero`
`labelRu` был `"Hero"` — единственная английская подпись среди 10 типов
секций (остальные девять — полностью русские: «О компании», «Услуги»,
«Преимущества», «Тарифы», «Отзывы», «Галерея», «Контакты», «Подвал», и
десятая — «Призыв к действию», но её `descriptionRu` начинался с
акронима `"CTA — ..."`, тоже нарушая единообразие языка).

**Починка:**
- `src/content/sectionLibrary.ts`: `labelRu: "Hero"` → `labelRu: "Обложка"`
  (общепринятый в русскоязычных конструкторах сайтов термин для
  hero-блока, ближайший идиоматичный аналог, не калька). Заодно
  `descriptionRu` секции `cta` — `"CTA — финальный блок..."` →
  `"Призыв к действию — финальный блок..."`, чтобы описание не
  начиналось с английского акронима.
- `src/routes/EditorScreen.tsx`: тост `"Добавьте секцию Hero перед
  экспортом"` и подсказка `"Добавьте видимую секцию Hero, чтобы
  включить экспорт"` — оба обновлены на `«Обложка»`, иначе сообщение
  об ошибке ссылалось бы на секцию, которой в списке уже нет под таким
  именем.
- `src/components/IconButton.tsx` — синхронизирован doc-комментарий,
  цитирующий то же сообщение.
- Тесты не проверяли текст `"Hero"` буквально ни в одном месте —
  переименование не потребовало правок тестов, `npm test` зелёный.

**Чем проверено:** `labels_check.mjs` — все 10 подписей в диалоге
«Добавить секцию» получены и распечатаны: `["Обложка","О компании",
"Услуги","Преимущества","Тарифы","Отзывы","Галерея","Призыв к
действию","Контакты","Подвал"]` — единообразно на русском. Скриншот
`final-library-dialog.png`.

## Дополнительно: 404 в консоли при загрузке

**Причина.** `index.html` не объявлял `<link rel="icon">` вовсе — браузер
по умолчанию всё равно запрашивает `/favicon.ico`, которого не было ни
в `public/`, ни где-либо ещё (папки `public/` не существовало), отсюда
`404` в консоли при каждой загрузке приложения.

**Починка.** Создан `public/favicon.svg` (SVG-монограмма «N» на
плашке цвета `--nd-color-accent`) и подключён явно в `index.html`:
`<link rel="icon" type="image/svg+xml" href="/favicon.svg" />`. Vite
копирует `public/*` в корень и `dist/` при сборке без дополнительной
настройки — проверено (`ls dist/` содержит `favicon.svg` рядом с
`index.html`).

**Чем проверено:** сетевые логи Playwright (`response.status()`) на
полном прогоне (`full_verify.mjs`) — `BAD RESPONSES (4xx/5xx): []`,
`curl -I http://localhost:5173/favicon.svg` → `200`.

## Дефект 4 (найден координатором после первой сдачи) — чипы «Отрасль»/«Тон» обрезаются без прокрутки

**Причина.** `.nd-chip-group__grid` — CSS grid с `grid-template-columns:
repeat(2, 1fr)` (`repeat(1, 1fr)` для тона), а на `@media (min-width: 1200px)`
— `repeat(4, 1fr)` для обеих групп. Брейкпоинт был завязан на ширину
**окна**, а не на реальную ширину контейнера этой сетки — а она разная
в двух местах использования: ~320/380px в сайдбаре «Настройки»
редактора (эта ширина не растёт после первого попадания в диапазон
768–1200px, дальше она константа) и до 640px в мастере
`/new` (`.nd-container-narrow`). При окне ≥1200px обе группы получали
4 узкие колонки по `1fr` — а `1fr`-трек по умолчанию не сжимается
ниже min-content своего содержимого (для чипа без переносов — ширины
самого длинного слова: «консалтинг», «e-commerce», «Минималистичный»);
сумма этих min-content-ширин четырёх колонок оказалась больше 347px
реальной ширины сайдбара, и поскольку `overflow-x: visible` — часть
чипов уезжала за край панели без возможности прокрутки или клика.

**Починка** (`src/styles/app.css`, `.nd-chip-group__grid` и `.nd-chip`):
1. `grid-template-columns: repeat(2, 1fr)` / `repeat(4, 1fr)` в двух
   местах и отдельный медиа-запрос — заменены на одно правило
   `grid-template-columns: repeat(auto-fit, minmax(min(140px, 100%), 1fr));`
   без брейкпоинтов по ширине окна: число колонок теперь считается
   браузером по **реальной** ширине контейнера в каждом конкретном
   месте использования (сайдбар редактора и мастер — независимо), а не
   по предположению «окно шире → колонок больше», которое было верно
   для мастера, но не для сайдбара с потолком в 380px. `min(140px, 100%)`
   в нижней границе `minmax` — чтобы даже при контейнере уже 140px
   (гипотетически) колонка не потребовала больше места, чем есть.
   Отдельный класс-модификатор `.nd-chip-group__grid--tone` (раньше
   задававший 1/4 колонки) убран за ненадобностью — `ChipGroup.tsx`
   по-прежнему добавляет класс `nd-chip-group__grid--tone` (пропс
   `layout="grid-tone"` не трогали), просто для него больше нет
   отдельного CSS-правила, это безвредно.
2. `.nd-chip` — добавлены `min-width: 0` (чтобы сам чип как grid-item
   не навязывал контейнеру свой min-content, как в дефекте 2 с
   `.nd-editor__preview-col`) и `overflow-wrap: anywhere` — страховка
   на случай ещё более узкого контейнера в будущем: даже слово без
   пробелов при реальной нехватке места переносится посимвольно, а не
   вылезает за край.
