# Техзадание: CleanLink

## Суть
Веб-агрегатор клининговых компаний по городам («Aviasales для клининга»): клиент ищет компанию по своему городу, сравнивает рейтинг и цены, заказывает услугу и переписывается с исполнителем; компания ведёт профиль, принимает заказы и следит за статистикой.

## Пользователи и роли

| Роль | Что делает | Что видит |
|---|---|---|
| Гость (не авторизован) | Ищет компании по городу, открывает карточки компаний, читает отзывы и прайс | Главный экран поиска, публичные карточки компаний (без чата и заказа — по кнопкам предлагается зарегистрироваться) |
| Клиент | Регистрируется, ищет компании, оформляет заказ, пишет в чат, оставляет отзыв после выполненного заказа, добавляет в избранное | Личный кабинет: заказы, избранное, отзывы, чаты |
| Компания (не верифицирована) | Зарегистрирована, но профиль виден в поиске в урезанном виде: фото/видео, название, контакты — без цен, акций, вкладок и приёма заказов | Заглушка «профиль на модерации» в своём кабинете, базовое редактирование данных |
| Компания (верифицирована) | Полный профиль: услуги/цены, акции, приём и обработка заказов, ответы на отзывы, статистика | Админ-панель компании: заказы, услуги, акции, отзывы, статистика |

Верификация в MVP — ручной флаг `is_verified` в БД (выставляется через сид/админ-эндпоинт), без внешнего интеграционного KYC-сервиса — см. «Осознанно вне объёма».

## Функции MVP

| ID | Функция | Приоритет | Критерий приёмки |
|---|---|---|---|
| F1 | Регистрация и логин (JWT: access + refresh в HttpOnly cookies), раздельные формы для роли «клиент» (email, пароль, username, город) и «компания» (email, пароль, company_username, ИНН/ОГРН, город, адрес, телефон, сайт, часы работы) | must | Пользователь заполняет форму своей роли, получает ошибку при занятом username/email, после успешной регистрации автоматически залогинен и видит свой кабинет; при неверном пароле логин отклоняется с понятным сообщением |
| F2 | Поиск компаний по городу с автодополнением (список городов из уже сохранённых в D1, кэшируется в KV) | must | Пользователь вводит первые буквы города, видит подсказки из существующих городов; выбрав город, видит список всех компаний в этом городе или пустое состояние «компаний пока нет» |
| F3 | ТОП-3 компании города по формуле `rating_score = avg_rating*0.6 + normalized_orders_count*0.3 + normalized_response_speed*0.1` (нормализация — min-max по компаниям того же города) | must | На экране города выделен блок «ТОП-3» с тремя компаниями, отсортированными по убыванию `rating_score`; при пересчёте после нового заказа/отзыва порядок обновляется при следующей загрузке страницы |
| F4 | Карточка компании: обложка, аватар, название, username, рейтинг (звёзды), город, контакты, вкладки «Услуги и цены», «Отзывы» (пагинация + сортировка по дате/оценке), «О нас» | must | Открыв карточку, пользователь переключает 3 вкладки без перезагрузки страницы; в «Отзывах» смена сортировки видимо переупорядочивает список; для неверифицированной компании вкладки «Услуги» и «Акции» скрыты, показана только базовая информация и контакты |
| F5 | Заказ услуги: клиент выбирает услугу из прайса компании и создаёт заказ со статусом `created`; компания получает заказ в своей панели и меняет статус (`created → in_progress → done`, либо `cancelled`) | must | Клиент нажимает «Заказать», заказ появляется в его кабинете со статусом «создан»; компания видит новый заказ в своей панели и может сменить статус; клиент видит актуальный статус после обновления страницы |
| F6 | Чат клиент-компания, привязанный к паре (client_id, company_id) | must | Клиент нажимает «Написать в чат» на карточке компании, чат создаётся (если ещё не существовал), сообщения отправляются и появляются у обеих сторон при обновлении/поллинге в течение 5 секунд; список чатов клиента отсортирован по времени последнего сообщения |
| F7 | Отзывы: клиент может оставить один отзыв (оценка 1-5 + текст) только к заказу в статусе `done`; компания может ответить на отзыв текстом | must | Кнопка «Оставить отзыв» доступна только у выполненных заказов без отзыва; повторная попытка оставить отзыв к тому же заказу блокируется; ответ компании отображается под отзывом сразу после отправки |
| F8 | Избранное: клиент добавляет/убирает компанию из избранного, видит список избранного в кабинете | must | Клик по иконке «сердце» на карточке компании переключает состояние избранного без перезагрузки; список в кабинете «Избранное» соответствует помеченным компаниям |
| F9 | Акции/скидки компании: верифицированная компания создаёт акцию (название, процент скидки, срок действия), акция отображается в карточке компании до истечения срока | must | Компания создаёт акцию через форму в своей панели, акция сразу видна в публичной карточке компании; после наступления `valid_until` акция перестаёт отображаться в публичной карточке (проверка по дате на сервере при выдаче) |
| F10 | Статистика компании: количество просмотров карточки, количество заказов по статусам, средний чек, конверсия (заказы/просмотры) в виде таблицы и простого графика | must | Верифицированная компания открывает вкладку «Статистика» и видит числа, совпадающие с фактическим количеством записей в БД (заказы, просмотры) за выбранный период |
| F11 | Три темы оформления (тёмная, светлая-градиент, классика) с переключателем и сохранением выбора в localStorage | must | Клик по переключателю темы мгновенно меняет цветовую схему всего интерфейса; после перезагрузки страницы выбранная тема сохраняется |
| F12 | Личный кабинет клиента: список заказов с фильтром по статусу | should | Клиент открывает «Мои заказы», видит все свои заказы, фильтр по статусу скрывает заказы других статусов |
| F13 | Просмотр профиля компании увеличивает счётчик просмотров (используется в F10) | should | Каждое открытие публичной карточки компании увеличивает `companies.views_count` на 1 (дедупликация по сессии в течение часа — необязательна для MVP) |

## Правила и валидация
- Все входные данные валидируются схемами Zod на бэкенде перед записью в D1; ошибка валидации → 400 с полем и понятным текстом.
- `username` и `company_username` уникальны в рамках таблицы `users` (одно пространство имён); проверка при регистрации до создания записи, конфликт → 409.
- Пароль ≥ 8 символов, хранится только как хэш (bcrypt/scrypt через Web Crypto), сырой пароль никогда не логируется и не возвращается в ответах API.
- Отзыв можно оставить только к заказу со статусом `done`, принадлежащему текущему клиенту, и только один раз (UNIQUE по order_id); повторная попытка → 409.
- Смена статуса заказа доступна только компании-владельцу заказа (`orders.company_id = companies.id` текущего пользователя) и только в допустимой последовательности (`created → in_progress → done|cancelled`); недопустимый переход → 400.
- Акция скрывается из публичной выдачи, если `valid_until < текущая дата` (проверка на сервере при каждом запросе карточки, не полагаемся на клиента).
- Услуги, акции, вкладка «Заказать» скрыты для компаний с `is_verified = 0` — как на бэкенде (эндпоинты возвращают ограниченный набор полей), так и на фронтенде.
- Чат между конкретной парой (client_id, company_id) уникален — при повторном «Написать в чат» открывается существующий чат, а не создаётся новый.
- Rate limiting: не более 100 запросов в минуту на пользователя/IP к API (упрощённая реализация на KV-счётчиках, см. «Упрощено для MVP»); превышение → 429.
- Все ответы API, содержащие пользовательский текст (отзывы, сообщения чата, описания), экранируются на фронтенде при рендере (React делает это по умолчанию; дополнительная санитизация HTML не требуется, т.к. rich-text ввод не поддерживается).
- SQL-инъекции исключаются использованием только parameterized-запросов D1 (`.bind()`), сырая конкатенация строк в SQL запрещена во всём бэкенд-коде.

## Состояния экранов

**Главный экран (поиск)**
- Пустое: город не выбран — показывается приглашение ввести город и, опционально, список последних популярных городов.
- Загрузка: скелетоны карточек компаний на месте списка.
- Ошибка: сообщение «Не удалось загрузить компании» с кнопкой «Повторить».
- Обычное: блок ТОП-3 + список остальных компаний города.
- Много данных: список компаний ниже ТОП-3 пагинируется (по 12 на страницу) или подгружается по скроллу.

**Карточка компании**
- Пустое: у неверифицированной компании — упрощённый вид без вкладок и прайса; у услуг/отзывов без записей — «Пока нет услуг»/«Пока нет отзывов».
- Загрузка: скелетон обложки, аватара, вкладок.
- Ошибка: «Компания не найдена» (404) с возвратом на поиск.
- Обычное: полный профиль с тремя вкладками.
- Много данных: отзывы пагинируются (по 10), прайс-лист со скроллом при >15 услугах.

**Личный кабинет клиента (заказы)**
- Пустое: «У вас пока нет заказов» с кнопкой «Найти компанию».
- Загрузка: скелетон списка.
- Ошибка: баннер с кнопкой «Повторить загрузку».
- Обычное: список заказов с фильтром по статусу.
- Много данных: пагинация по 20 заказов.

**Чат**
- Пустое: «Нет сообщений — начните диалог» в открытом, но пустом чате; «Нет активных чатов» в списке чатов.
- Загрузка: скелетон списка сообщений.
- Ошибка: «Не удалось отправить сообщение», сообщение остаётся в поле ввода для повтора.
- Обычное: лента сообщений с разделением по отправителю, автоскролл к последнему.
- Много данных: подгрузка истории при скролле вверх (по 30 сообщений за раз).

**Панель компании (заказы/статистика)**
- Пустое: «Заказов пока нет» / «Данных недостаточно для графика».
- Загрузка: скелетоны таблицы и графика.
- Ошибка: баннер с повтором запроса.
- Обычное: таблица заказов с действиями по смене статуса, блок графиков статистики.
- Много данных: пагинация заказов, агрегация статистики по выбранному периоду (7/30/90 дней) вместо построчного вывода.

## Принятые допущения

1. **Верификация компаний** делается вручную флагом `is_verified` в БД (через сид-скрипт/служебный эндпоинт для админа), без интеграции со сторонним ИНН/ОГРН-верификатором — в РФ нет бесплатного публичного API для этого без ключа.
2. **2FA (TOTP)** — реализуется как рабочая опциональная функция (генерация секрета, QR-код, проверка кода через `otplib`), но не входит в обязательный сценарий регистрации/логина по умолчанию — включается пользователем добровольно в настройках, чтобы не блокировать основной happy path тестирования.
3. **Восстановление пароля по email** — реализуется как рабочий флоу с генерацией токена и отправкой письма через Resend API, если пользователь предоставит `RESEND_API_KEY`; при отсутствии ключа — переключается в режим "вывести ссылку восстановления в ответе API / в логах сервера" (рабочий fallback для локальной разработки и демо без внешнего платного сервиса), это явно вынесено в disabled-режим по умолчанию.
4. **Реалтайм-чат** — если Durable Objects + WebSocket поднимаются штатно на выбранном окружении, используется этот механизм; если он окажется нестабильным при сборке/тестировании, чат работает через REST API с поллингом раз в 3-5 секунд с тем же UI/UX (пользователь не заметит разницы, кроме небольшой задержки). Решение принимает архитектор/бэкенд-инженер на следующем шаге конвейера, оба варианта дают одинаковый наблюдаемый результат для F6.
5. **3D-ковёр на главном экране** — реализуется CSS 3D-перспективой (`transform: perspective/rotateX/rotateY` по движению мыши) вместо React Three Fiber/Three.js, чтобы не тянуть тяжёлую 3D-библиотеку и не рисковать временем сборки; визуальный эффект «наклона и вращения» сохраняется.
6. **Workers AI (модерация отзывов, генерация описаний)** — реализуется как реально работающий вызов Workers AI (`@cf/...` текстовая модель) при наличии биндинга `AI` в окружении; если биндинг недоступен в текущем окружении сборки/тестов, используется локальный rule-based fallback (простой фильтр по стоп-словам для модерации, шаблонная генерация описания без ИИ) — код рабочий в обоих случаях, ни один из режимов не является пустышкой.
7. **Push-уведомления через Service Worker** — реализуются как рабочая функция (permission request + показ уведомления при новом заказе/сообщении, пока вкладка открыта), без внешнего push-сервера (Web Push с VAPID отложен — см. «Вне объёма»), т.к. это требует дополнительной инфраструктуры подписки и не критично для MVP.
8. **Email-уведомление о новом заказе** — рабочий вызов Resend API при наличии ключа, иначе — то же уведомление логируется в R2/консоль сервера как «отправленное письмо» (тот же код пути, другой транспорт).
9. **Шифрование AES-256-GCM** применяется к чувствительным полям, которые действительно чувствительны в этой модели данных — ИНН/ОГРН компании и содержимое сообщений чата в состоянии покоя (at rest) в D1; пароли по-прежнему хранятся только хэшированными (не шифрованными), это отраслевой стандарт.
10. **Rate limiting 100 запросов/мин** реализуется через счётчик в KV с TTL 60 секунд на ключ `ip:user_id`, а не через выделенный внешний сервис — этого достаточно для защиты на уровне Workers без дополнительной инфраструктуры.
11. **Логирование действий в R2** реализуется как построчный JSON-лог (append через периодическую агрегацию в Queue-consumer или прямую запись объекта с уникальным именем на каждое значимое действие) — не претендует на полноценную SIEM-систему, это базовый аудит-трейл.
12. **Обои на задний фон (кастомная загрузка + галерея R2)** входят в MVP в упрощённом виде: галерея из 4-6 предустановленных фонов (статические ассеты, не требующие R2 на старте) + один слот «загрузить своё фото» в R2 для авторизованного пользователя. Полноценная модерация загруженных обоев не входит в MVP.
13. **Cropper.js для аватаров** включён как рабочая функция обрезки перед загрузкой в R2.
14. **Cloudflare Queues** используются для очереди «новый заказ → уведомление компании»; если в среде сборки Queues недоступны, тот же обработчик вызывается синхронно в рамках запроса создания заказа (тот же результат для пользователя — компания видит заказ и уведомление, — разница только во внутреннем механизме доставки).
15. Валюта — российский рубль, суммы — целые числа без копеек, форматирование `₽` на фронтенде.
16. Единственный язык интерфейса — русский; интернационализация не предусмотрена.
17. Нормализация компонентов формулы рейтинга (`normalized_orders_count`, `normalized_response_speed`) — min-max нормализация в пределах компаний одного города на момент запроса; при единственной компании в городе оба нормализованных значения принимаются равными 1.

## Осознанно вне объёма

- **Полноценная KYC/юридическая проверка ИНН/ОГРН через внешний реестр (ФНС API)** — требует платного/лицензированного доступа, которого нет; в MVP это текстовое поле с базовой валидацией формата.
- **Web Push с VAPID-подпиской и доставкой уведомлений при закрытой вкладке** — требует подписки пользователя, хранения ключей и отдельного воркера-отправителя; оставляем только внутривкладочные уведомления через Service Worker.
- **Многоязычность (i18n)** — не нужна для целевого рынка MVP (РФ), усложнила бы объём без явной пользы.
- **Множественные исполнители/сотрудники внутри компании с назначением конкретного человека на заказ** — усложняет модель данных (нужна отдельная таблица `employees`); в MVP заказ назначается на компанию целиком, без учёта конкретного исполнителя.
- **Онлайн-оплата (эквайринг)** — нет ключей платёжного провайдера и явного разрешения на работу с деньгами в этом цикле; заказы в MVP создаются без предоплаты, оплата — по факту оффлайн между клиентом и компанией.
- **Модерация фото/видео контента через AI (image moderation)** — Workers AI используется только для текста (отзывы/описания); визуальная модерация загружаемых фото не входит в MVP.
- **Продвинутая аналитика с когортами, воронками, экспортом отчётов** — в MVP статистика ограничена базовыми метриками из F10 (просмотры, заказы по статусам, средний чек, конверсия) за выбранный период.
- **SSR/SEO-пререндеринг на уровне Cloudflare Pages для каждой карточки компании** — в MVP делаем базовые мета-теги через `react-helmet`-подобный подход на клиенте плюс статический `sitemap.xml`/`robots.txt`; полноценный SSR отложен, т.к. требует отдельной архитектуры рендеринга.
- **Полное покрытие интеграционными тестами (Supertest) каждого эндпоинта** — в MVP тестами (Vitest) покрываются только критические функции: формула рейтинга, переходы статусов заказа, уникальность username/отзыва, rate-limit счётчик; остальное — по возможности в рамках оставшегося времени конвейера.
- **CI/CD с husky pre-commit хуками и полным eslint/prettier конфигом уровня enterprise** — базовая настройка eslint/prettier входит, husky-хуки — по возможности, не блокируют сдачу MVP.
